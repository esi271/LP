Uguaglianza strutturale vs fisica

  • Strutturale (=, <>): confronta il contenuto dei valori, scendendo ricorsivamente nella struttura.

    let s = "ciao";;

    Restituirà false perchè sono due indirizzi diversi.

Funzioni e costrutti

In OCaml (come nel $\lambda$-calcolo) una funzione è un valore come un altro: può essere:

  • passata come argomento
  • restituita
  • assegnata ad un nome
  • lasciata anonima

Definizione

La forma esplicita è:

let <nome> = fun <parametri> -> <corpo>

Dove:

  • fun <parametri> -> <corpo> è la funzione
  • let <nome> = ... è solo un’etichetta attaccata a quel valore.

Altrimenti abbreviando:

let <nome> <parametro> = <corpo>

Posso anche riferirmi alla stessa funzione con un’etichetta diversa:

let succ = fun x -> x + 1;;
let succ' = succ;;

succ non è altro che un’alias, stesso valore ma etichetta diversa.

Funzione anonima

Una funzione anonima è una funzione senza label ad etichettarla:

fun x -> x+1;;

Più parametri

Non esiste davvere una funzione a $n$-argomenti: è una catena di $n$ funzioni a un argomento, annidate.
Questo è proprio ciò che rende possibile l’applicazione parziale.

let f = fun x -> fun y -> fun z -> <corpo>

O più compatto:

let f x y x = <corpo>

Applicazione

Per applicare una funzione basta fare:

f x

Questo corrisponde a $f(x)$, stesso ragionamento anche per funzioni anonime:

(fun x -> x + 1) 2

Le funzioni sono associative a sinistra

f a1 a2 a3;;

corrisponde a:

(((f a1) a2) a3);;

Il corpo

Il corpo di una funzione non va visto proprio come una sequenza di comandi, ma come delle espressioni valutate e restituirà l’ultima istruzione valutata.

let <nome> <x> =
    <exp1>;
    <exp2>;
    <exp3>;;
(*Restituisce exp3*)

Corpo semplice

let succ x =
    x + 1;;

In questo caso il corpo è già un’unica espressione.

If-then-else

let fact n acc =
    if n <= 1 then acc
    else n;;

Il risultato è il valore del ramo effettivamente valutato. Entrambi i rami devono avre lo stesso tipo.
Si possono concatenare più rami:

if ... then
else if ... then
else ...;;

Nomi temporanei locali

È possibile introdurre valori intermedi o funzioni ausiliarie locali con la sintassi:

let <ausiliaria> = <espressione> in <resto_del_corpo>

Ad esempio:

let idx l x =
    let rec idx2 l x acc =
        if (List.hd l) == x then acc
        else idx2 (List.tl l) x (acc + 1)
    in idx2 l x 0;;

In questo caso idx2 fa il lavoro sporco ma resta nascosta a chi usa idx.
Catene di let...in si annidano implicitamente, uno dentro al successivo:

let calcolo x =
    let a = x + 1 in
    let b = a * 2 in
    let c = b - 3 in
    c;;

Dentro un let ... in, and può essere usato per collegare più valori definiti allo stesso livello, calcolati indipendentemente l’uno dopo l’altro:

let s = ...
and t = ...
in ...

Pattern matching

Il pattern matching serve a scomporre il valore stesso mentre decide quale ramo prendere, e dà accesso diretto ai pezzi interni:

match expression with
    | pattern1 when boolean_expression -> expression1
    | pattern2 when boolean_expression -> expression2
    | _ -> expression3;;

I rami vengono provati in ordine dall’alto verso il basso e vince il primo che corrisponde.
_ è il catch-all.

Possiamo omettere nella dichiarazione della funzione il parametro su cui andiamo a fare pattern matching usando questo zucchero sintattico:

let func = function
    | pattern1 when boolean_expression -> expression1
    | pattern2 when boolean_expression -> expression2
    | _ -> expression3;;

È possibile include nel pattern matching più espressioni e poi matchare con i vari pattern:

match expression1, espression2 with
| pattern1, pattern2 when boolean_expression -> expression3
| pattern1, pattern2 when boolean_expression -> expression4
| _ -> expression5;;

Ricorsione

Per dichiarare una funzione ricorsiva dobbiamo usare la keyword rec nella sua dichiarazione, altrimenti la funzione non sarà visibile nel suo corpo e dunque non potrà essere chiamata:

let rec f n =
    ... f...;;

A seconda di come viene fatta la chiamata ricorsiva distinguamo tra:

  • Ricorsione non in coda: rimane del lavoro da fare dopo la chiamata ricorsiva, quindi ogni chiamata resta in attesa sullo stack.

    let rec fact n =
    if n <= 1 then 1
    else n * fact (n-1);;

    Dopo la chiamata resta da moltiplicare e quindi si accumulano gli stack.

  • Ricorsione in coda: la chiamata ricorsiva è l’ultima operazione, e quindi si comporta come un ciclo senza accumulo di stack.

    let rec fact_aux n acc =
    if n <= 1 then acc
    else fact_aux (n-1) (n*acc);;

    Niente da fare dopo la chiamata.

Il trucco per trasformare una funzione ricorsiva in tail-recursive è quasi sempre lo stesso: introdurre un accumulatore che porta il risultato parziale, invece di lasciarlo sospeso nello stack.

Mutua ricorsione tra funzioni

Quando più funzioni si chiamano a vicenda (non solo sé stessa), let rec da solo non basta ma serve collegarle con and, così che tutti i nomi siano visibili contemporaneamente in tutti i corpi fin dall’inizio:

let rec is_even = function
    | 0 -> true
    | 1 -> false
    | n -> is_odd (n-1)
and is_odd = function
    | 0 -> false
    | 1 -> true
    | n -> is_even (n-1);;

Collezioni e tipi definiti dall’utente

Collezioni

Liste

let l = [e1; e2; e3; ...; en];;

Sono:

  • Omogenee.
  • immutabili: quando sembra che modifichiamo una lista, magari con l’operatore cons, in realtà ne stiamo creando una nuova.
  • Acesso sequenziale.

Operatori

Tra gli operatori di base abbiamo:

  • cons ::

    Indica la concatenazione tra un elemento e una lista: e :: l.

    e :: [e1; e2; e3];;

    Otteniamo [e; e1; e2; e3].
    Può essere usato per fare pattern matching strutturale della lista:

    match l with
    | hd :: tl ->...;
    | [] -> ...

  • concatenazione @

    Concatena due liste:

    [e1; e2] @ [e3; e4];;

    Otteniamo [e1; e2; e2; e4].
    È un operatore inefficiente, per questo motivo è preferibile usare cons.

Modulo List

Del modulo List alcuni metodi di uso frequente sono:

  • List.length l: restituisce la dimensione di l.
  • List.hd l: restituisce la testa di l.
  • List.tl l: restituisce la lista data senza il primo elemento.
  • List.nth l n: restituisce l’$n$-esimo elemento di l.
  • List.rev l: restituisce la lista inversa di l.
  • List.append l0 l1: aggiunge l1 a l0.
  • List.rev_append l1 l2: inverte l1 e lo concatena con l2.
  • List.concat ll : concatena la lista di lista ll in un’unica lista.

Tuple

Sono liste eterogenee di lunghezza fissa:

let a_tuple = (5, 'a', "a string");;

È possibile accedere agli elementi tramite pattern matching strutturale:

match a_tuple with
    | (e1, e2, e3) -> ...
    | _ -> ...

Le coppie

Quando definisco una coppia:

let a_pair = (1, "w");;

Posso usare i metodi:

  • fst a_pair: accedo al primo elemento.
  • snd a_pair: accedo al secondo elemento.

Tipi definiti dall’utente

Alias

È il modo più semplice per definire un nuovo tipo: consiste nel dare un nuovo nome a un tipo esistente.
Qualsiasi tipo può essere “aliasato”.

type int_pair = int*int;;
let a : int_pair = (1,3);;

Varianti

Un tipo variante elenca tutte le possibili forme dei valori di quel tipo.
Ogni caso è identificato da un nome che inizia con la maiuscola, chiamato costruttore.

type variant =
    | Nothing
    | Integer of int
    | Record of {name : string; mutable age : int};;

Questi costruttori personalizzati sono usabili nel pattern matching strutturale, eventualmente ignorando le informazioni che non mi servono:

match variant with
    | Nothing -> ...
    | Integer _ -> ... (*qua non mi serve sapere il contenuto*)
    | Record {name = n; age = a} -> ...

Tipi mutualmente ricorsivi

Un tipo mutualmente ricorsivo deve essere dichiarato tramite la keyword and, così che tutti i nomi siano visibili contemporaneamente in tutte le definizioni:

type card = Card of regular | Joker
    and regular = { suit : card_suit; name : card_name; }
    and card_suit = Heart | Club | Spade | Diamond
    and card_name = Ace | King | Queen | Jack | Simple of int;;

Sistema dei moduli

Introduzione ai moduli

I moduli sono usati per realizzare tipi di dati astratti (e relative implementazioni) e per collezionare funzioni.

Sono composti da 2 parti:

  • Pubblica interfaccia (opzionale) sig ... end
  • L’implementazione del modulo struct ... end
module A:
    sig
        ...
    end =
    struct
        ...
    end;;
  • Abstract type → sig.
  • Implementazioni →struct.

Nella maggior parte dei casi non conviene fare tutto insieme nello stesso file, anzi conviene avere un file per l’interfaccia e uno o più files le varie implementazioni che rispettano l’interfaccia.

Structure struct ... end

(*Implementazione.ml*)
module A =
    struct

        type t1 = ...
        type t2 = ...
        exception ...

        let f1 ...
        let f2 ...
        let f3 ...
    end;;

Se importiamo ed usiamo questo modulo abbiamo accesso a tutte le funzioni e al vero tipo dei tipi che abbiamo dichiarato.

Usando l’interprete per importarlo basta fare:

# #use "Implementazione.ml";;
# A.f1 ...;;

Con #use il contenuto del file viene inserito nell’interprete come se lo avessi scritto a mano: il modulo A finisce nell’ambiente globale e il nome del file non conta, quindi non serve nessun prefisso.

Signature sig ... end

Le signature sono contenute in file .mli e sono le interfacce. Al loro interno posso definire operazioni pubbliche del mio tipo di dato ed eventualmente opacizzare il tipo:

(*Interfaccia.mli*)
module type B =
    sig
        type t1

        val f1 : <tipo_input> -> <tipo_output>
    end;;

In questo caso chi utilizzerà l’interfaccia sa solo che esiste questo tipo astratto t1: ne vedrà solo il nome, non la rappresentazione concreta.

Tipi astratti e tipi concreti

Consideriamo questo esempio:

module type Ex =
    sig
        type t1                  
        type t2 = int * int      
        type t3 = A | B of int   

        val f1 : t1 -> t2
    end;;
  • type t1 è astratto: chi usa l’interfaccia vede solo il nome, non la rappresentazione.
  • type t2 = int * int è concreto: la definizione fa parte dell’interfaccia, quindi chi usa il modulo sa che t2 è int * int e può usarlo come tale. Non viene opacizzato.
  • Per varianti e record vale lo stesso: se riporto la definizione nella signature, costruttori e campi restano accessibili; se la ometto, sono nascosti.

Rispetto all’implementazione, la signature:

  • opacizza i tipi dichiarati senza definizione,
  • nasconde le operazioni non elencate,
  • lascia trasparenti i tipi dichiarati con definizione.

Quindi devono contenere:

  • dichiarazioni dei tipi (astratti e/o concreti),
  • descrizione della funzione specificando nome, tipi argomenti e del risultato.

Per caricarle nell’interprete:

# #use "Interfaccia.mli";;

Il module type B entra direttamente nell’ambiente globale, quindi lo si usa come B, senza prefisso.

Coercizione di modulo

Posso prendere una struct che implementa la struttura richiesta da un’interfaccia B (quindi tipi e funzioni), e vederla attraverso questa interfaccia.

Esempio da interprete:

# #use "Interfaccia.mli";;
# #use "Implementazione.ml";;
# module C = (A : B)

Ora usando il modulo C io vedrò solo:

  • il tipo t1 che sarà astratto <abstr>.
  • la funzione f1.

Tutto il resto, presente nella struct ma non specificato dall’interfaccia viene oscurato e non è più visibile.

# C.f2;;
Error: Unbound value C.f2
# C.f1 ...;;
- : C.t1 = <abstr>

Vincolare il modulo a un’interfaccia direttamente

Invece di definire prima A e poi fare la coercizione module C = (A : B), posso dichiarare l’interfaccia direttamente nella definizione del modulo:

module A : B =
    struct
        ...
    end;;

Il risultato è lo stesso della coercizione e se la struct non rispetta la signature il compilatore dà errore.

La differenza con la coercizione di modulo è che in questo caso non resta il modulo originale A tutto visibile come invece avremo con la coercizione.

Rendere visibile un tipo astratto: with type

with type modifica una signature rendendo noto (uguale a un tipo concreto) un tipo che altrimenti sarebbe astratto.
Il resto della signature rimane opaco.

Consideriamo questa sig:

module type Set =
    sig
        type elt
        type t
        val empty : t
        val add : elt -> t -> t
    end;;

  • Senza with type:

    module IntSet : Set =
    struct

        type elt = int
        type t = int list

        let empty = []

        let add x s =
            if List.mem x s then s else x :: s

    end;;

    # #use "SetADT.mli";;
module type Set =
sig type elt type t val empty : t val add : elt -> t -> t end

# #use "IntSet.ml";;
module IntSet : Set

# IntSet.add 1 (IntSet.empty);;
Error: This expression has type int but an expression was expected of type IntSet.elt

    In questo caso all’interno di IntSet.ml i tipi astratti dell’interfaccia sono implementati con degli alias e quindi la firma di add sarebbe:
    add : int -> int list -> int list.
    Fuori, però, il vincolo : Set nasconde questi alias e la vista esterna è:
    IntSet.add : IntSet.elt -> IntSet.t -> IntSet.t

    IntSet.elt è un tipo opaco, diverso da int, e nessuna funzione della signature restituisce un elt: non posso crearne nessun valore e il modulo è inutilizzabile.

  • Con with type:

    module IntSet : (Set with type elt = int) =
    struct

        type elt = int
        type t = int list


        let empty = []

        let add x s =
            if List.mem x s then s else x :: s

    end;;

    # #use "SetADT.mli";;
module type Set =
    sig type elt type t val empty : t val add : elt -> t -> t end

# #use "IntSet.ml";;
module IntSet :
    sig type elt = int type t val empty : t val add : elt -> t -> t end

# IntSet.add 1 (IntSet.empty);;
- : IntSet.t = <abstr>

    with type elt = int rende visibile l’uguaglianza elt = int, è ciò che permette di passare 1 ad IntSet.add.
    Senza di esso IntSet sigilla elt come un tipo nuovo e nessun valore potrà entrarci.

    Invece t resta nascosto.

Regole utili:

  • Si può usare solo su tipi dichiarati senza definizione nella signature (type t): non si può ridefinire un tipo già concreto.

  • Più vincoli si concatenano con and:

    S with type key = int and type value = string.

  • Le parentesi attorno a Set with type elt = int sono facoltative.

  • Funziona su qualsiasi signature: moduli semplici, coercizioni e funtori.

Interfacce e moduli compilati nell’interprete

Nell’interprete si può caricare l’implementazione con #use e usare un’interfaccia compilata. Bisogna aprire ocaml nella stessa cartella in cui c’è il .cmi.

Qui A non ha prefisso (viene da #use, che incolla il contenuto), mentre B lo ha (viene dal .cmi).

Funtori

Introduzione

In OCaML si può avere moduli in cui si chiamano altri moduli, quindi si introduce il concetto di modulo parametrico.

I funtori sono “funzioni” da strutture a strutture.

Prendono in input un modulo, che rispetta una certa signature, e produce in output un nuovo modulo.

Concettualmente questa è la sua struttura:

module Funtore (ParametroModulo : SignatureRichiesta) =
    struct
        (* Implementazione che usa ParametroModulo*)
    end;;

Con:

  • Funtore il nome del funtore
  • ParametroModulo è l’input del mio funtore che deve rispettare la signature specificata da SignatureRichiesta.

Questo significa che una volta fissate le signature delle strutture di input, i dettagli implementativi possono cambiare senza avere effetti su nessuno dei moduli che li utilizzano.

Ci sono tre fondamenti da tenere a mente:

  • i parametri di un funtore devono essere a loro volta moduli o altri funtori, non può essere un valore concreto
  • i nomi devono avere l’iniziale maiuscola e i parametri dei funtori vanno chiamati tra parentesi.
  • i moduli e i funtori non sono di prima classe.

Un funtore da solo non è un modulo utilizzabile, ha bisogno di essere istanziato. Se da una parte il funtore rende polimorfo un certo modulo, dall’altra quando viene instanziato il modulo collassa ad essere monomorfo con l’implementazione passata al modulo.

Esempio con interprete

Consideriamo questa signature StackADT.mli:

    sig
        type char_stack
        exception EmptyStackException
        val empty : char_stack
        val push : char_stack -> char -> unit
        ...
    end;;

Questo funtore balanced.ml:

module UnboundedStack =

        let push stack c = ...

Polimorfismo in ML

Introduzione

Il polimorfismo permette di gestire valore di tipi di dato diversi utilizzando un’interfaccia uniforme.

  • Una funzione che può essere valutata o applicata a valori di tipi diversi è nota come funzione polimorfica.
  • Un tipo di dato che può apparire come un tipo generalizzato è definito tipo di dato polimorfico.

Il polimorfismo non è solo un vezzo teorico: è il meccanismo che permette di scrivere codice riusabile senza sacrificare la sicurezza di tipo (type safety).
OCaml/ML supporta nativamente il polimorfismo:

let compose f g x = f (g x);;

# #use "compose.ml" ;;
val compose : ('a -> 'b) -> ('c -> 'a) -> 'c -> 'b = <fun>

Tipologie di polimorfimo

  • Polimorfismo Ad Hoc:

    la funzione/metodo denota implementazioni diverse a seconda di un insieme di tipi e delle loro combinazioni.
    È supportato in molti linguaggi tramite l’overloading (sovraccarico).

    int sum(int a, int b) { return a + b; }
double sum(double a, double b) { return a + b; }
String sum(String a, String b) { return a + b; }

  • Polimorfismo Parametrico:

    tutto il codice è scritto senza menzionare alcun tipo specifico e quindi può essere usato in modo trasparente con un numero qualsiasi di nuovi tipi; è ampiamente supportato nei linguaggi di programmazione funzionale a tipizzazione statica, oppure nell’orientamento agli oggetti tramite generics o template.

    class Box<T> {
    private T content;
    T get() { return content; }
    void set(T value) { content = value; }
}

  • Polimorfismo di Sottotipo (Subtype):

    il codice sfrutta l’idea di sottotipi per restringere l’insieme di tipi utilizzabili in un particolare caso di polimorfismo parametrico; nei linguaggi OO è realizzato tramite ereditarietà e sotto-classamento (sub-classing).

    abstract class Animal { abstract String verso(); }
class Cane extends Animal { String verso() { return "Bau"; } }
class Gatto extends Animal { String verso() { return "Miao"; } }
void faiVerso(Animal a) { System.out.println(a.verso()); }

Polimorfismo parametrico

OCaml supporta il polimorfismo parametrico.
compose implementa $f \circ g$ senza alcun legame di tipo; il suo tipo (polimorfico) è:: $$ (\alpha \to \beta) * (\gamma \to \alpha) * \gamma \to \beta$$

$\alpha$, $\beta$ e $\gamma$ sono variabili di tipo indicate rispettivamente con 'a , 'b e 'c.

Tipizzazione debole

Nulla che sia il risultato dell’applicazione di una funzione a un argomento può essere polimorfico:

se non conosciamo ancora esattamente il suo tipo, allora si tratta di un tipo debole.

Il tipo è inferito “time to time”:

  • Il tipo 'a -> 'a significa che per ogni tipo 'a , questo è il tipo 'a -> 'a.
  • Il tipo '_a -> '_a significa che esiste uno e un solo tipo '_a tale per cui questo è il tipo '_a -> '_a.
# let compose f g x = f (g x);;
val compose : ('a -> 'b) -> ('c -> 'a) -> 'c -> 'b = <fun>

# let compose' = compose (fun c -> int_of_char c) ;;
val compose' : ('_a -> char) -> '_a -> int = <fun>

Possiamo quindi dire che ciò che è potenzialmente polimorfico diventa monomorfico nella pratica, quando il compilatore si trova a gestire la sua forma polimorfica.

Esempio

# let a = ref [];;
val a : '_a list ref = {contents = []}

# let b = 1::!a ;;

val b : int list = [1]

# a;;
- : int list ref = {contents = []}

La funzione ref

ref è una funzione predefinita di OCaml che crea una cella mutabile (un riferimento):

val ref : 'a -> 'a ref = <fun>

Per accedere al contenuto puntato si usa !.

  • ref [] crea un riferimento il cui contenuto iniziale è la lista vuota [] . Poiché in fase di dichiarazione non sappiamo ancora che tipo di lista conterrà (lista di interi? di stringhe? di altro?), OCaml gli assegna il tipo 'a list ref .
  • ma essendo ref [] il risultato dell’applicazione di una funzione (ref applicata a []) viene reso debolmente polimorfico: '_a list ref.
  • Quando costruisce la nuova lista b il compilatore risolve il tipo '_a list ref $\to$ int list ref e a ora avrà tipo concreto int list ref.

L’operazione di puntare la lista la rende debole e una volta che il compilatore “indovina” il tipo, questo rimane.

Usare il polimorfismo parametrico

Dichiarazione

  • Tipo polimorfico:

    type 'a <nome> = ...

    Dove 'a è la variabile di tipo (il parametro), <nome> è il nome del tipo che si sta definendo:

    type 'a option =
    | None
    | Some of 'a;;

  • Argomenti polimorfici:

    let f (x : 'a) = ...

    Oppure come si fa quasi sempre in pratica, senza annotazione esplicita e lasciando che sia il compilatore a inferire il tipo:

    # let f x = ...
val f : 'a -> ...

Errore comune

module Stack = struct
    type 'a stack = { mutable c : 'a list }
    exception EmptyStackException

    let empty = { c = [] }
    let push s x = s.c <- x :: s.c
    let pop s =
        match s.c with
          hd::tl -> s.c <- tl
        | [] -> raise EmptyStackException
end;;

# #use "adtstack.ml";;
# let s = Stack.empty;;
val s : '_a Stack.stack = {Stack.c = []}

# Stack.push s 7;;
- : unit = ()

# Stack.push s 25;;
- : unit = ()

# s ;;
- : int Stack.stack = {Stack.c = [25; 7]}

# let s1 = Stack.empty;;

val s1 : int Stack.stack = {Stack.c = [25; 7]}

# Stack.push s1 "Hello";;

Error: This expression has type string but an expression was expected of type int

empty è un valore unico condiviso definito una sola volta nel modulo, non una funzione che ne crea uno nuovo a ogni chiamata.
Il suo tipo '_a Stack.stack resta debole, e al primo uso concreto (Stack.push s 7) si “monomorfizza” a int Stack.stack per sempre, in tutto il programma.
Ecco perché anche s1 , pur essendo una nuova variabile OCaml, condivide lo stesso tipo concreto ormai fissato: non è un bug di s1, è che Stack.empty stesso è già diventato int Stack.stack a livello di modulo.

Sistemiamo rendendo empty una funzione:

module Stack = struct
    type 'a stack = { mutable c : 'a list }
    exception EmptyStackException

    let empty () = { c = [] }
    let push s x = s.c <- x :: s.c
    let pop s =
        match s.c with
          hd::tl -> s.c <- tl
        | []-> raise EmptyStackException
end;;

Argomenti opzionali con valore di default

In molti metodi potremmo avere la necessità di utilizzare un argomento opzionale con valore di default.

let rec count ?(tot=0) x = function
    | [] -> tot
    | h::l1 -> 
        if (h==x) then count ~tot:(tot+1) x l1 else count ~tot:tot x l1

Con questa sintassi dichiariamo la presenza di un argomento opzionale tot che di default varrà 0.
Quando bisogna aggiornare il valore di questo argomenti bisogna usare la sintassi: ~<nome>:(<new_val>) che in sostanza dice di passare <new_val> come argomento con etichetta <nome>.
La presenza di un argomento opzionale ricade anche sui tipi dedotti dal compilatore:

val count : ?tot:int -> 'a -> 'a list -> int = <fun>

In OCaml un argomento opzionale deve essere definito prima di un argomento posizionale.

Iterare e maneggiare le stringhe

Non possiamo iterare sul contenuto di una stringa usando il pattern matching strutturale, nulla ci vieta di usare un indice per la posizione e accedervi al carattere corrispondente:

let rec iter f ?(k = 0) s =
    if k < String.length s then ( f s.[k] ; iter f ~k:(k + 1) s ) ;;

Un altro approccio è quello di ottenere a partire dalla stringa una lista di caratteri.

Definire un operatore

                    @ [h] @
                   (qsort (List.filter (fun x -> (h >: x)) tl) )
    in qsort l

In questo caso abbiato definito l’operatore >: che verrà utilizzato come un operatore infisso all’interno della mia funzione.

Currying & Partial Evaluation

Currying

Il currying è una tecnica per trasformare una funzione con più argomenti in una catena di funzioni, ciascuna con un singolo argomento (applicazione parziale).
Ad es.,

$$f(x,y) = \frac{y}{x} \xrightarrow{(2)} f(2) = \frac{y}{2} \xrightarrow{(3)} f(2)(3) = \frac{3}{2}$$

Il currying è una tecnica predefinita in ML.

# let f x y z = x+.y*.z;;
val f : float -> float -> float -> float = <fun>

# f 5.;;
- : float -> float -> float = <fun>

let f x y z = ... è solo zucchero sintattico per:

let f = fun x -> fun y -> fun z -> x +. y *. z

Quindi f è una funzione che prende solo x e restituisce un’altra funzione, che prende solo y e restituisce un’altra funzione, che prende solo z.
Quindi il primo argomento passato va sempre a x, il secondo a y, il terzo a z.

Valutazione parziale

Si riferisce al processo di fissare un certo numero di argomenti di una funzione, producendo un’altra funzione di arità minore.
Ad es.

$$f(x,y) = \frac{y}{x} \xrightarrow{(x=2)} g(y) =f(2, y) = \frac{y}{2} \xrightarrow{(3)} g(3) = \frac{3}{2}$$

# let f x y = y/.x ;;
val f : float -> float -> float = <fun>

# let g = f 2. ;;
val g : float -> float = <fun>

Il vantaggio si presenta quando definisco una funzione usando dei parametri con nome, in questo caso posso specificare la posizione e controllare quale funzione otterrò:

# let compose ~f ~g x = f (g x)
val compose : f:('a -> 'b) -> g:('c -> 'a) -> 'c -> 'b = <fun>

# let compose' = compose ~g: (fun x -> x**3.)
val compose' : f:(float -> 'a) -> float -> 'a = <fun>

Map, Filter and Reduce

Panoramica

  • map = applicare una funzione a tutti gli elementi della lista;
  • filter = filtrare alcuni elementi dalla lista in base a un predicato;
  • reduce = ridurre l’intera lista a un singolo valore secondo una funzione cumulativa.

Rappresentano il pattern di programmazione più ricorrente nella programmazione funzionale.

Map

Ricordiamo una possibile implementazione di map:

let rec map f = function
    | h::l1 -> f h::map f l1
    | _ -> [];;

Il modulo List ha la sua implementazione di map:

# List.map;;
val map : ('a -> 'b) -> 'a list -> 'b list

Filter

Anche per filter non è complesso fornirne un’implementazione:

let rec filter p = function
    [] -> []
    | h::l -> if p h then h :: filter p l else filter p l;;

Ma anche in questo caso il modulo List ha la sua implementazione:

  • List.filter f l: restituisce tutti gli elementi della lista l che soddisfano il predicato f.

Reduce

Anche per reduce vediamo una possibile implementazione:

let rec reduce acc op = function
    [] -> acc
    | h::tl -> reduce (op acc h) op tl ;;

Folding

reduce è un esempio di folding (piegatura), ossia, iterare una funzione binaria arbitraria su un insieme di dati costruendo progressivamente un valore di ritorno.

Le funzioni possono essere associative in due modi (sinistro e destro), quindi il folding può essere realizzato:

  • right fold:
    combinando il primo elemento con il risultato della combinazione ricorsiva del resto, ad es.

    $$0 + (1 + (2 + (3 + (7 + (25 + 4)))))$$

  • left fold:
    combinando il risultato della combinazione ricorsiva di tutti gli elementi tranne l’ultimo, con l’ultimo

Il modulo List fornisce le funzioni:

  • List.fold_left f acc l:

    val fold_left : ('acc -> 'a -> 'acc) -> 'acc -> 'a list -> 'acc

    Consideriamo la lista $[e1, e2, e3, e4]$

  • List.fold_right f l acc:

    val fold_right : ('a -> 'acc -> 'acc) -> 'a list -> 'acc -> 'acc

Approfondimento sulle funzioni

Funzioni con un numero variabile di argomenti

I variadici, sono funzioni chiamabili con un numero variabile di elementi.
Possiamo costruire in OCamL una serie di funzioni per ottenere questo riusultato.

OCaml non ha funzioni variadiche native. Il trucco è far sì che ogni argomento venga consumato da una funzione che restituisce un’altra funzione, e che il risultato venga passato avanti come “accumulatore”.

let arg x = fun y rest -> rest (op x y) ;;
let stop x = x;;
let f g = g init;;
  • arg x: è una funzione parzialmente applicata.
    Aspetta ancora y (l’accumulatore corrente) e rest (il “resto della catena”).
    Quando li riceve, calcola op x y e lo passa a rest.
  • op: funzione che spiega come combinare il nuovo argomento x con l’accumulatore y.
  • init: il valore iniziale dell’accumulatore.
  • stop: l’identità. Chiude la catena e restituisce l’accumulatore finale.
  • f g = g init: avvia la catena, passando init alla prima funzione.
# let op = fun x y -> x+y;;
val op : int -> int -> int = <fun>

# let init = 0;;
val init : int = 0

varargs.ml usa op e init senza definirli: vanno quindi definiti prima di caricare il file.
Al momento del #use, arg e f si legano ai valori che op e init hanno in quell’istante. Se in seguito li ridefinisco, devo ricaricare il file.

# #use "varargs.ml";;
val arg : int -> int -> (int -> 'a) -> 'a = <fun>
val stop : 'a -> 'a = <fun>
val f : (int -> 'a) -> 'a = <fun>

f (arg 1) (arg 2) (arg 7) (arg 25) (arg (-1)) stop;;
- : int = 34

Funtore per funzioni con un numero variabile di argomenti

L’approccio precedente deve essere ricaricato ogni volta che serve un tipo diverso per f.
Questo perchè op e init sono nomi globali. Se voglio passare da somma di interi a lista di stringhe, devo ridefinire op e init e ricaricare il file.
Non si può avere le due versioni contemporaneamente.

Una soluzione è usare un funtore: prende un modulo come parametro e restituisce un modulo.
Qui serve che arg, stop e f non dipendano da un op e un init globali, ma da quelli di un modulo che viene passato.

Servono tre pezzi.

  • un tipo di dato astratto (OpVarADT):

    module type OpVarADT = sig
    type a and b and c
    val op : a -> b -> c
    val init : c
end

  • Il funtore VarArgs:

    module VarArgs (OP : OpVarADT.OpVarADT) = struct
    let arg x = fun y rest -> rest (OP.op x y)
    let stop x = x
    let f g = g OP.init
end

    Il codice è lo stesso di prima, ma op e init diventano OP.op e OP.init, cioè quelli del modulo ricevuto.

    Ci dice che per usare VarArgs, serve un modulo che rispetti la signature OpVarADT che definisce tre tipi a, b, c, un’operazione op e un valore iniziale init.

  • Le implementazioni concrete:

    module Sum = struct
    type a = int and b = int and c = int
    let op = fun x y -> x + y
    let init = 0
end

module StringConcat = struct
    type a = string and b = string list and c = string list
    let op = fun (x: string) y -> y @ [x]
    let init = []
end

Ora non ci resta che applicare il funtore:

# #use "OpVarADT.mli";;
# #use "sum.ml";;
# #use "concat.ml" ;;
# #use "varargs.ml" ;;

# module M0 = VarArgs(StringConcat) ;;
# module M1 = VarArgs(Sum) ;;

# M1.f (M1.arg 1) (M1.arg 2) (M1.arg 7) M1.stop;;
- : Sum.c = 10

# M0.f (M0.arg "Hello") (M0.arg "World") (M0.arg "!!!") M0.stop ;;
- : StringConcat.c = ["Hello"; "World"; "!!!"]

Ogni applicazione produce un modulo nuovo, già specializzato. Ora si può usare entrambi nella stessa sessione, senza ricaricare nulla.

Funtore di funtore

Consideriamo di fare la stessa cosa di prima ma con delle liste generiche.
Per StringConcat abbiamo scritto a mano il tipo string ma ora vogliamo un unico modulo ListConcat che funzioni per qualsiasi 'a list.
Ma la signature OpVarADT vuole tipi semplici (a, b, c), senza parametri come invece sarebbe 'a, quindi non puoi scrivere:

module ListConcat = struct
  type a and b = a list and c = a list
  ...
end

Qui a è un tipo astratto, cioè senza definizione: per il compilatore non è int, né string, né niente. Quando poi si prova M2.arg "Hello", il compilatore risponde che “Hello” è una string ma si aspettava un ListConcat.a, e nessun valore concreto ha quel tipo.

Funtore anche per il tipo

Se non puoi parametrizzare con 'a, parametrizzi con un modulo che contiene il tipo:

module ListConcatFunctor (T : sig type t end) = struct
  type a = T.t and b = a list and c = a list
  let op = fun (x: a) y -> y @ [x]
  let init = []
end

T : sig type t end è un modulo che contiene solo un tipo t, e a viene definito come T.t.
Ora il tipo è concreto, ma lo scegli tu al momento dell’uso:

module M3 = VarArgs(ListConcatFunctor(struct type t = int end))
module M4 = VarArgs(ListConcatFunctor(struct type t = string end))

Qui ci sono due funtori annidati:

  • prima ListConcatFunctor costruisce un modulo “concatena liste di int” (o di string),
  • poi VarArgs lo trasforma in arg/stop/f specializzati.
# M3.f (M3.arg 2) (M3.arg 3) (M3.arg 4) M3.stop;;
- : int list = [2; 3; 4]

# M4.f (M4.arg "Hello") (M4.arg "World") M4.stop;;
- : string list = ["Hello"; "World"]

Introduzione

Erlang overview

Erlang è un linguaggio funzionale a tipizzazione dinamica orientato alla concorrenza:

il processo è l’unità di base di ogni computazione.

Erlang adotta il modello ad attori (actor’s model) per la concorrenza, basato su:

  • scambio di messaggi asincrono: gli attori mandano messaggi senza attendere la risposta.
  • memoria non condivisa: ogni attore è visto come una singola persona.

Erlang supporta:

  • la distribuzione
  • la fault tolerance
  • hot-swapping: l’aggiornamento dinamico del software

Shell Beam

Erlang viene eseguito su macchina virtuale attraverso la BEAM, che costituisce il suo ambiente di esecuzione.
È stata progettata per eseguire i programmi Erlang e gestire in modo efficiente la concorrenza.

Gli attori di Erlang sono dei light process, estremamente più leggeri ma diversi rispetto ai processi tradizionali gestiti dal sistema operativo.
La gestione di questi processi viene affidata alla Beam che li schedula e distribuisce l’esecuzione sui processori disponibili.

In questo modo il sistema operativo gestisce solo la macchina virtuale, mentre la Beam si occupa della gestione dei processi Erlang e della loro concorrenza.

Per avviare l’ambiente interattivo basta eseguire:

erl

  • Compilare moduli:

List Comprehension

[ X || Qualificatore1, ..., QualificatoreN ]

X calcola ogni elemento della lista risultante; ogni qualificatore è un generatore oppure un filtro:

  • Un generatore ha la forma Pattern <- Lista ed estrae uno alla volta gli elementi della lista.
  • Un filtro è un predicato o un’espressione booleana: gli elementi per cui vale false vengono scartati.

Senso di lettura

Si legge da sinistra a destra dopo il ||, come dei cicli annidati. L’espressione a sinistra del || si valuta per ultima.

  • Il primo generatore è il ciclo più esterno.
  • Ogni qualificatore successivo è più interno: un eventuale secondo generatore gira per intero a ogni elemento del primo.
  • Un filtro si applica alle variabili già legate dai qualificatori alla sua sinistra. Non può usare variabili legate più a destra.
  • Solo per le combinazioni che superano tutti i filtri si valuta l’espressione iniziale.
1> [X*X || X <- [1,2,3,4]].
[1,4,9,16]

2> [{X,Y} || X <- [1,2], Y <- [a,b]].
[{1,a},{1,b},{2,a},{2,b}]

Variabili e pattern matching

Variabili

Una variabile è solo un nome legato a un valore e non può essere modificata.

Quindi non ci sono vere e proprie “variabili” nel senso letterale: questo perchè non possono variare.

  • Il nome inizia con una lettera maiuscola.
  • _ è la variabile anonima: combacia con qualsiasi valore e non lega nulla.
  • Le legature si creano tramite pattern matching.

Come funziona =

Il simbolo = non è un’assegnazione ma un confronto con legatura.

Erlang cerca di far combaciare il pattern a sinistra con il valore a destra:

  • Le variabili ancora libere vengono legate.
  • Quelle già legate devono avere lo stesso valore.

Vediamo degli esempi:

1> A = 1.
1

2> A = 2.
** exception error: no match of right hand side value 2

In questo caso nel 1 lego A a 1, poi provo a cambiare il valore e ottengo errore.
Questo perchè non si può cambiare il valore a cui è legata.

3> [B|L] = [a,b,c].
[a,b,c]

4> {A,B,L}.
{1,a,[b,c]}

In questo caso nel 3 B viene legata ad a e L a [b,c].

5> {X, X} = {B, B}.
{a,a}

6> {Y, Y} = {X, b}.
** exception error: no match of right hand side value {a,b}

Una variabile ripetuta nel pattern forza i due valori a essere uguali.


7> 1 = A.
1

8> 1 = Z.
* 1: variable 'Z' is unbound

Il lato destro non può contenere variabili non legate;

9> {A1, _, [B1|_], {B1}} = {abc, 23, [22,x], {22}}.
{abc,23,[22,x],{22}}

10> A1.
abc

11> B1.
22

_ ignora un elemento e B1 compare due volte, quindi 22 deve essere uguale nelle due posizioni.

Funzioni e Moduli

Funzioni

Una funzione è un insieme di clausole separate da ; e terminate da .

Le funzioni sono definite a tratti:

nome(pattern11, pattern12, ..., pattern1n) [when guardia1] -> corpo1 ;
nome(pattern21, pattern22, ..., pattern2n) [when guardia2] -> corpo2 ;
...
nome(patternk1, patternk2, ..., patternkn) [when guardiak] -> corpok .
  • Le clausole vengono provate in ordine finché una combacia.
  • Quando una clausola combacia, tutte le variabili della sua testa risultano legate.
  • Se nessuna clausola combacia si ottiene l’errore function_clause.
  • Il valore della funzione è quello dell’ultima espressione del corpo.
  • le espressioni nel corpo si separano con la virgola.
fact(0) -> 1;
fact(N) -> N * fact(N-1).

Il corpo

Il corpo delle clausole è composto da più espressioni separate da una virgola :

calcola(X) ->
    Y = X * 2,
    Z = Y + 10,
    Z.

Posso articolare maggiormente il corpo utilizzando case: permette di scegliere, tramite pattern matching, quale espressione eseguire in base al valore di un’espressione:

nome_funzione(Parametri) ->
    case Espressione of
        Pattern1 -> Espressione1;
        Pattern2 -> Espressione2;
        Pattern3 -> Espressione3;
        _ -> Espressione4
    end.

Può essere inserito in qualsiasi punto del corpo di una clausola:

calcola(N) ->
    X = N * 2,

    Y = case X of
        10 -> 100;
        20 -> 200;
        _ -> 0
    end,

    Y + 5.

Esiste anche la struttura if ... end:

if
    Condizione1 -> Espressione1;
    Condizione2 -> Espressione2;
    true -> EspressioneDefault
end

Le condizioni dell’if devono essere guardie, cioè espressioni ammesse nel contesto delle guardie.

Funzioni anonime

Una funzione anonima si definisce usando la keyword fun:

fun(Parametri) ->
    Espressione
end

Può essere a sua volta legata:

F = fun(X) -> X * 2 end.

F(2).

Guardie

Ogni clausola nella definizione di funzione può avere una condizione in più aggiungendo una sequenza di guardie dopo la keyword when.

  • Una guardia semplice è una sequenza di espressioni di guardia separate da virgole.
  • Un’espressione di guardia è un sottoinsieme delle espressioni di Erlang prive di effetti collaterali.
  • La sequenza è vera quando tutte le espressioni valgono true.

Quindi espressioni di guardia valide sono:

  • L’atomo true e altre costanti
  • Chiamate ad alcune funzioni predefinite (BIF).
  • Espressioni aritmetiche e booleane;
  • Espressioni a corto circuito (andalso, orelse).

BIF:
is_atom/1is_binary/1is_bitstring/1is_float/1is_function/2
is_function/1is_integer/1is_list/1is_number/1is_pid/1
is_port/1is_record/2is_record/3is_reference/1is_tuple/1
abs/1bit_size/1byte_size/1element/2float/1
hd/1length/1node/0node/1round/1
self/0size/1tl/1trunc/1tuple_size/1

Moduli

Erlang organizza i file tramite moduli: un modulo è un file .erl.
I file possono contenere diverse funzioni, caratterizzate per nome e arità, che vogliamo rendere accessibili:

-module(ex_module).
-export([double/1]).

double(X) -> double(X, 2).
double(X, N) -> X * N.
  • -module(nome).: nome deve coincidere con il nome del file
  • -export([nome/arità, ...]).: elenca le funzioni visibili dall’esterno. Dobbiamo specificare il loro nome i il numero di argomenti richiesti per ogni funzione che vogliamo rendere visibile.

In questo esempio double/1 si può chiamare da fuori, mentre double/2 è locale al modulo.
double/1 e double/2 sono funzioni diverse.

Actor Model Concurrency

Il problema della concorrenza

Il modello tradizionale è quello dei thread: il programma viene diviso in task che girano concorrentemente e operano sulla stessa memoria.
Da qui nascono due problemi classici:

  • Race condition con perdita di aggiornamento
  • Deadlock

Le soluzioni classiche (lock, mutex, semafori) spostano il problema sul programmatore. Erlang, e Scala tramite la libreria Akka, adotta un approccio diverso: l’Actor Model.

Il modello degli attori

Ogni oggetto è un attore, caratterizzato da:

  • una mailbox, dove i messaggi ricevuti vengono accodati;
  • un behavior, cioè come reagisce al prossimo messaggio.

La computazione è guidata dai dati: alla ricezione di un messaggio un attore può:

  • inviare un numero qualsiasi di messaggi ad altri attori;
  • creare un numero qualsiasi di nuovi attori;
  • assumere un nuovo behavior per gestire il messaggio successivo.

Proprietà fondamentali

  • La comunicazione è asincrona: il mittente non aspetta che il messaggio venga ricevuto. Non ci sono garanzie sull’ordine di ricezione tra mittenti diversi, ma i messaggi vengono prima o poi consegnati. Tra una coppia di processi, invece, i messaggi arrivano nell’ordine in cui sono stati inviati.
  • Non c’è stato condiviso: lo stato interno di un attore è privato e si legge o si modifica solo tramite messaggi.
  • Gli attori girano concorrentemente e sono implementati come lightweight user-space threads.

Concorrenza in Erlang

Tre elementi base:

  • spawn(): funzione built-in per creare nuovi attori;
  • !: operatore per inviare un messaggio a un altro attore;
  • receive: meccanismo di pattern matching per estrarre messaggi dalla mailbox.

spawn: creare processi

Pid = spawn(Modulo, Funzione, Args).

Con:

  • Modulo: atomo col nome del modulo.
  • Funzione: atomo col nome di una funzione definita ed esportata in Modulo.
  • Args: lista degli argomenti da passare. Gli elementi della lista diventano gli argomenti della Funzione, quindi la lunghezza di Args deve essere uguale all’arità di Funzione.

spawn crea un nuovo processo (un attore) che esegue Modulo:Funzione(Arg1, ..., ArgN) e restituisce subito il suo Pid, senza aspettare che la funzione finisca.
Padre e figlio proseguono poi in parallelo: il codice della funzione girerà nel processo figlio, non in quello che ha chiamato spawn.
Quindi anche se la funzione contiene un loop infinito (per esempio una wait/1 che si richiama ricorsivamente dentro un receive), il chiamante non resta bloccato: riceve il Pid e passa all’istruzione successiva.

Forma alternativa, senza modulo e funzione esportata:

Pid = spawn(fun() -> ... end).

Invio di messaggi

Ogni attore ha:

  • un indirizzo (Pid) che lo identifica;
  • una mailbox con i messaggi consegnati ma non ancora elaborati.

I messaggi sono ordinati per tempo di arrivo, non per tempo di invio. Per inviare un messaggio:

  • bisogna conoscere il Pid del destinatario;
  • si usa l’operatore !;
  • se serve una risposta, il messaggio deve includere il Pid del mittente (di solito self()).

La sintassi per inviare un messaggio è:

id_att ! mess

Dove:

  • id_att: deve identificare un attore
  • mess: può essere qualunque termine: un atomo, una tupla, una lista, anche il risultato di una chiamata di funzione. Viene prima valutata, poi il valore risultante viene inviato.
1> Pid ! "ciao" .
"ciao"

In Erlang tutto è un’espressione e ha un valore. L’operatore ! come valore restituisce il messaggio che ha inviato, nessuna conferma o messaggio di errore.

  • l’invio non blocca mai il mittente;
  • l’invio a un Pid non fallisce mai, anche se il destinatario non esiste o è irraggiungibile (con un nome registrato che non esiste, invece, si ha un errore badarg).

Ricezione di messaggi

Le operazioni di ricezione usano pattern matching:

receive
    Any -> do_something(Any)
end
  • l’attore prende dalla mailbox il messaggio più vecchio che matcha Any;
  • se la coda è vuota, resta bloccato in attesa e i messaggi non matchati restano in mailbox.
receive
    {Pid, something} -> do_something(Pid)
end

In generale:

receive
    Pattern1 [when GuardSeq1] -> Body1;
    ...
    PatternN [when GuardSeqN] -> BodyN
[after ExprT -> BodyT]
end

La definizione e valutazione delle regole sono simili a quelle delle funzioni:

  • il messaggio viene confrontato col pattern, e se la guardia è vera si esegue il corpo. Le clausole si separano con ; tranne per l’ultima.
  • Se nessun pattern matcha, l’attore aspetta: in un receive se nessun messaggio in mailbox matcha non succede nulla di grave. L’attore va in attesa finché non arriva un messaggio che matcha. I messaggi che non matchano restano in mailbox, e verranno riprovati al receive successivo.
  • con afterdopo ExprT millisecondi l’attore viene risvegliato ed esegue BodyT, così non aspetta per sempre;
  • con after 0 si controlla la mailbox senza bloccarsi.

Erlang scorre la mailbox dal messaggio più vecchio e prende il primo che matcha una qualche clausola, anche se non è il primo in coda. Se si accumulano messaggi che nessuna clausola riconosce, ogni receive li riscorre tutti e la mailbox può crescere a dismisura. Per questo conviene avere una clausola catch-all. Attenzione però: una catch-all scarta anche i messaggi che potevano servire a un receive successivo, quindi va usata sapendo cosa si perde.

Vita di un processo

Un processo Erlang esegue la funzione con cui è stato creato (quella passata a spawn). Non esiste un “ciclo principale” automatico: il processo vive finché quella funzione non termina.

Il ciclo di vita

  • Creazione: spawn crea il processo, gli assegna un Pid e lo mette in coda allo scheduler.
  • Esecuzione: lo scheduler gli dà tempo di CPU e il processo esegue il suo codice.
  • Attesa: quando raggiunge un receive e nessun messaggio matcha, il processo si blocca e non consuma CPU. Torna pronto quando arriva un messaggio che matcha (o scade l’after).
  • Terminazione: il processo muore quando la sua funzione ritorna (uscita normale) oppure quando si verifica un errore non gestito (uscita anomala, crash). Quando un processo muore il suo Pid esiste ancora come valore, ma non corrisponde più a nessun processo. Inviargli messaggi non dà errore: i messaggi si perdono.

Per controllare se un processo è vivo si usa is_process_alive(Pid).

Perché serve la ricorsione

Un receive gestisce un solo messaggio: prende quello che matcha, esegue il corpo e poi finisce. Se dopo il receive non c’è altro codice, la funzione ritorna e il processo muore.

% senza ricorsione: gestisce un messaggio e poi termina
loop() ->
    receive
        {toF, C} -> io:format("~p °C is ~p °F~n", [C, 32+C*9/5])
    end.

Per gestire altri messaggi, il processo deve rimettersi in ascolto: l’ultima cosa che fa è richiamare la funzione.

% con ricorsione: resta vivo
loop() ->
    receive
        {toF, C} ->
            io:format("~p °C is ~p °F~n", [C, 32+C*9/5]),
            loop()                % rimette il processo in attesa del prossimo messaggio
    end.

Così il processo fa questo: riceve un messaggio, lo elabora, richiama loop(), che torna al receive, e così via. Il processo “resta vivo” perché la sua funzione non arriva mai alla fine.

Il processo termina quando una clausola non richiama la funzione, come {stop} in questo esempio:

{stop} -> io:format("Stopping!~n");     % nessuna chiamata ricorsiva: la funzione ritorna, il processo muore

Ricorsione in coda

La chiamata ricorsiva è l’ultima espressione della clausola, quindi Erlang riusa lo stesso frame di stack invece di aggiungerne uno nuovo a ogni messaggio. Per questo un processo può girare per giorni e gestire milioni di messaggi senza far crescere lo stack. Se la chiamata ricorsiva non fosse in coda (per esempio 1 + loop()), lo stack crescerebbe a ogni messaggio.

Lo stato e il cambio di behavior

Dato che non c’è stato condiviso, lo stato di un processo vive negli argomenti della funzione ricorsiva. Ogni chiamata può passare un valore nuovo, ed è così che un attore “assume un nuovo behavior” o cambia stato:

contatore(N) ->
    receive
        incrementa     -> contatore(N + 1);
        {leggi, Da}    -> Da ! {valore, N}, contatore(N);
        stop           -> ok
    end.
  • spawn(fun() -> contatore(0) end) crea un contatore che parte da 0.
  • Il messaggio incrementa fa richiamare la funzione con N + 1: lo stato è cambiato.
  • Il messaggio {leggi, Da} risponde al mittente col valore corrente e lascia lo stato invariato.
  • stop non richiama la funzione e il processo termina. Anche il behavior può cambiare: invece di richiamare la stessa funzione si può richiamarne un’altra, e questa gestirà il messaggio successivo in modo diverso.

Alternativa: il dizionario di processo

Lo stato si può tenere anche nel dizionario di processo, una memoria privata di ogni processo, con put(Chiave, Valore) e get(Chiave). Ad esempio::

{From, {store, Key, Value}} -> put(Key, {ok, Value}), From ! {kvs, true}, loop();
{From, {lookup, Key}}       -> From ! {kvs, get(Key)}, loop()
  • put(Key, {ok, Value}) salva la coppia nel dizionario (se la chiave esiste, la sovrascrive);
  • loop() si richiama senza passare lo stato come argomento: il dizionario resta intatto tra una chiamata e l’altra;
  • get(Key) restituisce {ok, Value} se la chiave c’è, undefined altrimenti.

Nel codice reale si usa poco: è uno stato implicito e nascosto e si perde quando il processo muore. Di solito è meglio passare lo stato come argomento.

Altri modi di terminare

  • La funzione ritorna (il caso normale, descritto finora).
  • exit(Motivo) chiamata dal processo stesso per terminare.
  • Un errore non gestito (per esempio un pattern matching fallito o una divisione per zero) fa morire il processo con un motivo diverso da normal.
  • Arriva da fuori un exit signal che lo uccide: da un processo linkato che è morto con un motivo diverso da normal (una morte normal non uccide i processi linkati), oppure con exit(Pid, Motivo) mandato da un altro processo. Un processo che trappa le uscite (trap_exit) invece lo riceve come messaggio.

La shell è un processo

Anche la shell di un nodo è un normale processo, con un suo Pid e una sua mailbox:

1> self().
<0.80.0>

Tutto ciò che scrivi nel prompt viene eseguito da quel processo. Quando chiami una funzione che fa Pid ! {self(), ...} e poi receive, il self() è il Pid della shell, e la risposta arriva nella sua mailbox.

  • Si possono mandare messaggi alla shell come a qualunque altro processo; flush() stampa e svuota la mailbox.
  • Se un’espressione causa un errore, la shell viene riavviata con un Pid nuovo: self() prima e dopo l’errore dà due valori diversi, e i messaggi rimasti nella vecchia mailbox sono persi.
  • Ogni nodo ha la sua shell, quindi su due nodi diversi ci sono due processi distinti.

Scheduling

Gli attori non sono processi del sistema operativo e non sono gestiti da esso.

  • La BEAM (la macchina virtuale di Erlang) usa uno scheduler preemptive.
  • Quando un attore gira per troppo tempo, o raggiunge un receive bloccante, viene messo in pausa e rimesso nella coda di scheduling.

Attori e resto del sistema:

  • gli scheduler di Erlang e quelli del SO sono distinti, quindi applicazioni Erlang di lunga durata non rallentano i processi del SO;
  • la BEAM supporta il symmetric multiprocessing (SMP): può eseguire più attori in parallelo su più core;
  • ogni singolo attore resta sequenziale, senza parallelismo interno.

La concorrenza è avere molti attori in progresso (anche su un solo core), il parallelismo è eseguirli davvero nello stesso istante su core diversi.

I processi Erlang sono estremamente economici (nell’ordine del microsecondo) e se ne possono avere centinaia di migliaia. Questo permette lo stile “un attore per ogni entità concorrente”.

Named actors

Per rendere pubblico il Pid di un processo a tutti gli altri:

  • register(an_atom, Pid): associa il nome al Pid;
  • unregister(an_atom): rimuove l’associazione;
  • whereis(an_atom): restituisce il Pid oppure undefined;
  • registered(): restituisce la lista dei nomi registrati.

Una volta registrato, si può scrivere direttamente nome ! messaggio. Attenzione: se il nome non è registrato, nome ! messaggio solleva un errore badarg. È l’unico caso in cui l’invio può fallire (con un Pid, anche di un processo morto, non fallisce mai).

Errori nella programmazione concorrente

In Erlang, di norma, i processi sono isolati: se uno muore, gli altri non se ne accorgono a meno che non siano “collegati”.
Quando due processi sono correlati, gli errori di uno devono poter influenzare l’altro. Per questo esistono:

  • link: bidirezionali
  • monitor: unidirezionali.

Il meccanismo con cui un processo “avvisa” gli altri della propria morte è l’exit signal.

Gestione degli errori

Link

  • link(Pid) crea un collegamento tra il processo corrente e Pid.
  • Il link definisce un percorso di propagazione degli errori tra i due processi.
  • Se A è linkato a B e B muore, ad A viene mandato un exit signal. Vale anche il contrario: i link sono simmetrici.
  • L’insieme dei processi linkati a un dato processo si chiama link set.
  • Il segnale arriva (se A è un system process) come messaggio {'EXIT', Pid, Why}, dove Pid è il processo morto e Why il motivo.

Exit signals

  • Vengono generati da un processo quando muore.
  • Sono mandati in broadcast a tutti i processi del link set del processo che muore.
  • Contengono un argomento che spiega perché il processo è morto: lo si imposta con exit(Reason) oppure viene impostato implicitamente (per esempio badarith, badarg).
  • Quando un processo termina “naturalmente” (finisce la sua funzione) il motivo è normal.
  • Si possono mandare segnali esplicitamente con exit(Pid, X): il mittente non muore (è una “fake death”, il segnale è solo inviato a Pid).

I processi

  • Un Non System Process (processo normale) che riceve un exit signal muore anch’esso, a meno che il motivo sia normal.

  • Un System Process riceve il segnale come un normale messaggio nella mailbox, quindi lo può gestire.

    process_flag(trap_exit, true) trasforma un processo in system process.

Comportamento del ricevente

Il ricevente, a seconda del suo tipo di processo e dal segnale di exit che riceve, ha un coportamento diverso:

System Process: trap_exit = true

Exit SignalAzione
killil processo muore e manda in broadcast killed al suo link set.
XViene aggiunto {'EXIT', Pid, X} alla mailbox.

Non System Process: trap_exit = false

normalil processo continua e il segnale svanisce.
killil processo muore e manda in broadcast il segnale senza modificarlo al suo link set.
Xil processo muore e manda in broadcast il segnale senza modificarlo al suo link set.

In questo esempio solo A è un System Process.
kill è intrappolabile solo dal processo a cui viene mandato (cioè C, che ne è destinatario diretto) e lo uccide comunque.

Come scelgo di creare un processo?

  • Non mi interessa se il processo che creo crasha:

    Pid = spawn(fun() -> ... end).

  • Voglio morire anch’io se il processo che creo crasha:

    Pid = spawn_link(fun() -> ... end).

  • Voglio gestire l’errore se il processo che creo crasha:

    process_flag(trap_exit, true),
Pid = spawn_link(fun() -> ... end).

Monitor: link unidirezionali

I link sono simmetrici: se A muore, B riceve un exit signal e viceversa.
Per evitare che un processo muoia bisogna renderlo system process, cosa non sempre desiderabile.

Il monitor è un link asimmetrico.

  • Se A monitora B e B muore, ad A viene mandato un segnale.
  • Se A muore, a B non viene mandato nulla.

Creazione di un monitor che monitora B:

erlang:monitor(process, B)

  • Se B muore con motivo Reason, ad A arriva il messaggio:

    {'DOWN', Ref, process, B, Reason}

    dove Ref è il riferimento al monitor.
    Si possono avere monitor multipli sullo stesso processo, ciascuno con il suo Ref.

Il monitor è unidirezionale: ripetere la chiamata crea più monitor indipendenti, e ognuno manda un messaggio 'DOWN' quando B termina.

Introduzioni alla programmazione distribuita

I due modelli di distribuzione

Con la distribuzione possiamo spawnare processi su nodi e macchine remote, le primitive per fare ciò funzionano in modo trasparente su una rete nello stesso modo in cui funzionavano su un singolo nodo.

Programmi distribuiti sono programmi che sono progettati per essere eseguiti su reti di computer e che possono coordinare le proprie attività solo tramite lo scambio di messaggi.

Erlang offre due modelli:

  • Erlang distribuito (distributed Erlang)

    • le applicazioni girano su un insieme di computer strettamente accoppiati, chiamati nodi Erlang;
    • i processi possono essere creati (spawn) su qualunque nodo;
    • a parte lo spawn, tutto il resto funziona come sempre (stessa sintassi di send/receive, link, ecc.);
    • eseguito in un’ambiente fidato.

  • Distribuzione basata su socket (socket-based)

    • può funzionare in un ambiente non fidato (untrusted);
    • è meno potente (connessioni ristrette);
    • permette un controllo fine su cosa può essere eseguito su un nodo.

L’unità base su cui costruiamo un programma Erlang è il processo. Per costruire un programma Erlang distributito ci basterà spawnare i processi sulle macchine corrette.

Scrivere un programma distribuito

È consigliato lavorare al programma in un ordine specifico:

  1. Scrivere e testare il programma in una regolare sessione Erlang non distribuita (stesso nodo).
  2. Testare il programma su differenti nodi Erlang eseguiti sullo stesso computer.
  3. Testare il programma su differneti nodi Erlang eseguiti su diversi computer.

Erlang distribuito

Consideriamo come esempio un semplice name server kvs:

-module(kvs).
-export([start/0, store/2, lookup/1]).
 
start() -> register(kvs, spawn(fun() -> loop() end)).
 
store(Key, Value) -> rpc({store, Key, Value}).
lookup(Key) -> rpc({lookup, Key}).
 
rpc(Q) ->
    kvs ! {self(), Q},
    receive
        {kvs, Reply} -> Reply
    end.
 
loop() ->
    receive
        {From, {store, Key, Value}} ->
            put(Key, {ok, Value}), From ! {kvs, true}, loop();
        {From, {lookup, Key}} ->
            From ! {kvs, get(Key)}, loop()
    end.

Come funziona

  • start() avvia il server con il nome registrato kvs;
  • lookup(Key) restituisce il valore associato a Key nel name server;
  • store(Key, Value) associa Value a Key nel name server.
  • rpc/1 è la funzione client: manda al server kvs un messaggio {self(), Q} (il pid serve al server per rispondere) e aspetta {kvs, Reply}.
  • loop/0 è il server: riceve una richiesta, la gestisce, risponde con From ! {kvs, ...} e si richiama ricorsivamente (tail recursion) per mantenere lo stato.
  • Lo stato è tenuto nel dizionario di processo (put/2 e get/1). store salva {ok, Value}, per questo lookup restituisce {ok, Value}, mentre una chiave assente dà undefined.

Nodi separati sullo stesso computer

Creazione nodi

Creiamo 2 nodi Erlang sullo stesso computer, possiamo farlo aprendo 2 terminali e inizializzando il sistema Erlang specificando il nome del nodo usando erl -sname <name>:

$ erl -sname gandalf

Questo comando inizializza un nodo Erlang con il nome di gandalf sull’host locale. Il nome del nodo sarà nella forma Name@Host.
-sname usa nomi corti, e un nodo creato con -sname può comunicare solo con nodi creati con -sname.

Esempio

In questo modo ora possiamo mettere il server kvs su un nodo e con l’altro invieremo le richieste.

Server:

erl -sname sif

(sif@surtur)1> kvs:start().
true

Client:

erl -sname amora

(amora@surtur)1> rpc:call(sif@surtur, kvs, store, [weather, sunny]).
true

(amora@surtur)2> rpc:call(sif@surtur, kvs, lookup, [weather]).
{ok,sunny}

Se controllo lato server:

(sif@surtur)2> kvs:lookup(weather).
{ok,sunny}

Nodi su computer diversi

Creazione nodi

Per creare un nodo su computer che sono in reti diverse usiamo il comando: erl -name <name>

$ erl -name bilbo

-name usa nomi completi (fully qualified), inoltre un nodo creato con -name può comunicare solo con altri nomi creati con -name.

Cookie

Due nodi su reti diverse, per comunicare, devono essere nello stesso cluster e devono avere lo stesso magic cookie. Tre modi per impostarlo:

  1. salvarlo in $HOME/.erlang.cookie:

    echo "A Magic Cookie" > ~/.erlang.cookie
chmod 400 ~/.erlang.cookie

    Il chmod 400 rende il file leggibile solo dal proprietario.

  2. con l’opzione -setcookie:

    erl -setcookie "A Magic Cookie"

  3. con la BIF erlang:set_cookie:

    erl -sname sif
(sif@surtur)1> erlang:set_cookie(node(), 'A Magic Cookie').
true

I modi 1 e 3 sono più sicuri del 2 (con -setcookie il cookie resta visibile nella riga di comando, ad esempio con ps), e i cookie non viaggiano mai in chiaro sulla rete.

Esempio

Ora possiamo mettere il server kvs su un nodo e con l’altro invieremo le richieste.

Su una macchina thor:

erl -name sif -setcookie abc

(sif@thor)1> kvs:start().
true

Sulla macchina surtur:

erl -name amora -setcookie abc

(amora@surtur)1> rpc:call(sif@thor, kvs, store, [weather, warm]).
true

(amora@surtur)2> rpc:call(sif@thor, kvs, lookup, [weather]).
{ok,warm}

Se ricontrollo su thor:

(sif@thor)2> kvs:lookup(weather).
{ok,warm}

Comunicazione tra nodi e rpc

Un nodo è una VM Erlang autonoma, con un proprio spazio di indirizzamento e un proprio insieme di processi.

Come abbiamo visto negli esempi, il punto centrale di un programma distribuito consiste nella comunicazione tra i nodi: fondamentalmente che si trattino di nodi sullo stesso host o su computer diversi, i modi di comunicare tra di essi sono quelli che vedremo in questa sezione.

Scambio di messaggi

Per inviare il messaggio a un processo su un dato nodo, a patto di conoscere il suo Pid, possiamo continuare a usare:

Pid ! Msg

Altrimenti se sappiamo con quale nome tale processo è registrato localmente sul nodo possiamo usare:

{RegName, Node} ! Msg

Con questa sintassi inviamo un messaggio al processo registrato RegName sul nodo Node.

Libreria rpc

È una libreria di Erlang specifica per la distribuzione.
RPC sta per Remote Procedure Call: consente di chiamare una funzione che gira su un’altra macchina (o in un altro processo) come se fosse una normale chiamata locale: il chiamante invia la richiesta, aspetta e riceve il risultato, senza occuparsi dei dettagli della comunicazione.
Tra le funzioni principali abbiamo:

  • rpc:call(Node, Mod, Fun, Args):

    esegue Mod:Fun(Args) sul nodo Node e aspetta il risultato (sincrona). Se la chiamata riesce restituisce il valore; se fallisce restituisce {badrpc, Reason}, per esempio {badrpc, nodedown} se il nodo non è raggiungibile.

Cluster

Un cluster è l’insieme dei nodi connessi tra loro; per connettersi devono avere lo stesso cookie.

Due nodi con lo stesso cookie ma mai in contatto non sono ancora nello stesso cluster, affinché lo siano devono prima connettersi tramite:

  • invio di messaggio;
  • rpc:call;
  • spawn remoto.

Primitive per lavorare con i nodi del cluster

  • spawn(Node, Mod, Func, ArgList) -> Pid: crea un processo su un nodo remoto;
  • spawn_link(Node, Mod, Func, ArgList) -> Pid: come sopra, ma con link al processo creato;
  • disconnect_node(Node) -> bool() | ignored: disconnette il nodo;
  • monitor_node(Node, Flag) -> true: permette di essere avvisati se il nodo cade o si disconnette.

Primitive per orientarsi in un cluster

  • node():

    Restituisce il nome del nodo locale.

  • node(Arg):

    Restituisce il nodo dove Arg è situato. Arg può essere un Pid, un riferimento o una porta.

  • nodes():

    Restituisce una lista contentente gli altri nodi del network con il quale siamo connessi.

  • is_alive():

    Restituisce true se il nodo locale è vivo e può essere parte di un sistema distribuito, false altrimenti.

Libreria global

È una libreria di Erlang che fornisce un registro dei nomi condiviso fra tutti i nodi di un cluster.
Con register/2 (la versione locale) un nome vale solo all’interno di un singolo nodo, con global invece un processo può essere registrato con un nome visibile e univoco in tutta la rete di nodi connessi, così da poterlo raggiungere senza conoscerne il PID né il nodo su cui gira.
Tra le funzioni principali abbiamo:

  • global:register_name(Name, Pid):

    Questa funzione sincrona registra il processo Pid con il nome globale Name.
    Restituisce yes se la registrazione riesce, no se il nome è già in uso o se il Pid è già registrato con un altro nome.

  • global:whereis_name(Name):

    Cerca il processo registrato con il nome Name e ne restituisce il Pid, se non esiste alcuna registrazione con quel nome restituisce undefined.

Se il nodo su cui vive il processo cade, o il processo termina, la registrazione viene rimossa automaticamente.

Esempio spawning in un cluster

-module(ddemo).
-export([rpc/4, start/1]).
 
start(Node) -> spawn(Node, fun() -> loop() end).
 
rpc(Pid, M, F, A) ->
    Pid ! {rpc, self(), M, F, A},
    receive
        {Pid, Response} -> Response
    end.
 
loop() ->
    receive
        {rpc, Pid, M, F, A} ->
            Pid ! {self(), (catch apply(M, F, A))},
            loop()
    end.

Esempio d’uso:

erl -name sif -setcookie abc

(sif@surtur.di.unimi.it)1> Pid = ddemo:start('amora@thor.di.unimi.it').
<8745.43.0>

(sif@surtur.di.unimi.it)3> ddemo:rpc(Pid, erlang, node, []).
'amora@thor.di.unimi.it'
  • start(Node) crea sul nodo remoto un processo che esegue loop/0;
  • rpc/4 manda al processo remoto la richiesta di eseguire apply(M, F, A) e aspetta la risposta;
  • il risultato 'amora@thor.di.unimi.it' mostra che erlang:node() è stata davvero eseguita sul nodo remoto;
  • il pid <8745.43.0> ha il primo numero diverso da 0, segno che il processo non è locale;
  • catch serve a non far morire il server se la funzione chiamata solleva un’eccezione.

Group Leader

Il group leader è un concetto generale di Erlang, ma diventa rilevante nel cluster perché lo spawn remoto lo eredita dal nodo che crea il processo.
Ogni processo Erlang ha un group leader, cioè un altro processo a cui vengono inviate tutte le richieste di input/output del processo. Quando un processo chiama io:format/2, non scrive direttamente sul terminale: manda una richiesta di I/O al proprio group leader, che si occupa di eseguirla e di rispondere.
Il group leader viene ereditato dal processo padre: un processo creato con spawn ha lo stesso group leader di chi lo ha creato.

Questo vuol dire che in un sistema distribuito, un processo creato su un nodo remoto con una spawn eredita il group leader del processo che lo ha creato, anche se questo vive su un altro nodo. Per questo un io:format eseguito su b@host ma lanciato da a@host stampa il risultato sul terminale di a@host.

Per questi motivi, per far sì che un processo creato da un nodo stampi sul terminale del nodo in cui gira dovremo usare:

  • group_leader(GroupLeader, Pid):

    Specifica a Pid che da ora in avanti il suo group leader, e quindi destinatario del proprio I/O, è GroupLeader.

In questo esempio remoting.erl:

start(N, L) -> spawn(N, remoting, create, [L]).

create(L) ->
    group_leader(whereis(user), self()),
    global:register_name(L, self()),
    io:format("I'm the actor «~p» created on ~p and registered as ~p~n", [self(), node(), L]),
    wait().

start crea un processo sul nodo N che esegue create.

Appena creo il processo, specifico subito chi è il suo group leader.
user è il nome registrato del processo che gestisce l’I/O standard del nodo.

Erlang socket

Problema della distribuzione basata su spawn remota:

  • il client può eseguire qualsiasi processo sulla macchina del server;
  • esempio distruttivo: rpc:multicall(nodes(), os, cmd, ["cd /; rm -rf *"]) cancella i file su tutti i nodi connessi.

Quindi la distribuzione basata su spawn remota:

  • va benissimo quando si possiedono tutte le macchine e si vogliono controllare da una sola;
  • va bene quando siamo nella stessa LAN.
  • non è adatta quando le macchine appartengono a persone diverse, che vogliono controllare cosa viene eseguito sulle proprie.

Mentre la distribuzione basata su socket

  • usa una forma ristretta di spawn, in cui il proprietario della macchina ha il controllo esplicito su cosa viene eseguito;
  • si realizza con il modulo lib_chan.

lib_chan

lib_chan è un modulo che permette a un utente di controllare esplicitamente quali processi vengono creati sulle sue macchine.

Interfaccia:

  • start_server() -> true:

    avvia un server sull’host locale, il cui comportamento dipende dal file $HOME/.erlang_config/lib_chan.conf;

  • connect(Host, Port, S, P, ArgsC) -> {ok, Pid} | {error, Why}:

    prova ad aprire la porta Port sull’host Host e ad attivare il servizio S protetto dalla password P.

  • cast(Pid, Msg):

    invia un messaggio al servizio (Pid è quello restituito da connect) e non aspetta risposta (asincrono).
    cast manderà come messaggio {send, Msg} al proprio proxy, il servizio riceverà il messaggio {chan, MM, Msg}.

  • rpc(Pid, Msg):

    invia una richiesta e aspetta la risposta (sincrono).

    Il flusso di messaggi è lo stesso di cast: rpc manda {send, Msg} al proprio proxy e il servizio riceve {chan, MM, Msg}.
    Il servizio risponde con {send, Result} al proprio proxy, e il client, che tramite rpc era rimasto in attesa, riceve {chan, MM, Result} dal suo proxy e restituisce solo Result.

Il file di configurazione contiene tuple della forma:

  • {port, NNNN}: il server si mette in ascolto sulla porta NNNN;
  • {service, S, password, P, mfa, SomeMod, SomeFunc, SomeArgs}: definisce un servizio S protetto dalla password P.

Quando la connessione viene creata dal client invocando connect, due processi proxy vengono spawnati: uno sul lato client e l’altro sul lato server. Ora il server esegue lo spawn di un processo che esegue:

SomeMod:SomeFunc(MM, ArgsC, SomeArgs)

Dove:

  • MM è il pid di un processo proxy (middle man) usato per inviare messaggi al client;
  • ArgsC viene dalla chiamata connect del client;
  • SomeArgs viene dal file di configurazione (lato server).

Il punto chiave: il client non può eseguire codice arbitrario, può solo attivare i servizi che il proprietario ha esplicitamente elencato nel file di configurazione, e solo conoscendo la password.

Esempio

File di configurazione:

{port, 12340}.
{service, nameServer, password, "ABXy45", mfa, mod_name_server, start_me_up, notUsed}.

Questo significa che stiamo offrendo un servizio, protetto dalla password ABXy45 chiamato nameServer sulla porta 12340 del nostro computer.

Modulo del servizio, che fa da ponte verso kvs:

-module(mod_name_server).
-export([start_me_up/3]).
 
start_me_up(MM, _ArgsC, _ArgS) -> loop(MM).
 
loop(MM) ->
    receive
        {chan, MM, {store, K, V}} ->
            kvs:store(K, V), loop(MM);
        {chan, MM, {lookup, K}} ->
            MM ! {send, kvs:lookup(K)}, loop(MM);
        {chan_closed, MM} ->
            true
    end.

Messaggi da gestire

  • {chan, MM, Msg}: un messaggio arrivato dal client attraverso il proxy;
  • MM ! {send, Term}: invia Term al client;
  • {chan_closed, MM}: il client ha chiuso il canale, il servizio termina.

Lato server:

1> kvs:start().
true

2> lib_chan:start_server().
Starting a port server on 12340...
true

3> kvs:lookup(joe).
{ok,"writing a book"}

Lato client:

1> {ok, Pid} = lib_chan:connect("localhost", 12340, nameServer, "ABXy45", "").
{ok, <0.43.0>}

2> lib_chan:cast(Pid, {store, joe, "writing a book"}).
{send,{store,joe,"writing a book"}}

3> lib_chan:rpc(Pid, {lookup, joe}).
{ok,"writing a book"}

4> lib_chan:rpc(Pid, {lookup, jim}).
undefined

  • il server kvs gira sul nodo, ma il client lo raggiunge solo tramite il servizio nameServer, che espone soltanto store e lookup.

    }
}

object Upper {
    def upper(strings: String*) = strings.map(_.toUpperCase())
}
println(Upper.upper("A", "First", "Scala", "Program"))

La keyword object indica una classe a istanza singola. Non esistono metodi statici ma metodi di oggetti singleton.

Possiamo fare un ultimo refactor in modo da poterlo poi compilare.

object Upper { 
    def main(args: Array[String]) = {
        args.map(_.toUpperCase()).foreach(printf("%s ",_)) 
        println("") 
    } 
}

Type Hierarchy

La gerarchia dei tipi in scala è composta in questo modo

  • Any, la radice della gerarchia
    • AnyVal, la radice di tutti i tipi primitivi
    • AnyRef, la radice di tutte le reference classes (incluse java.* e scala.*). E’ l’equivalente della classe Object

Due tipi di valori “vuoti”

  • Null, per tutti i reference types. Ha una sola istanza null. Corrisponde al concetto di null del runtime
  • Nothing, è il sottotipo di tutti, non ha istanze. Usato per definire i tipi in modo sicuro es. List[Nothing]

Traits

In Java una classe può implementare un numero arbitrario di interfacce. Questo è utile dato che ci permette di dichiarare che la classe espone multiple astrazioni.

In molti casi le interfacce hanno sempre la stessa funzionalità, in cui parte è ortogonale ai membri della classe principale. Il termine mixin è usato per queste parti di codice riusabile.

package ui

class ButtonWithCallbacks(
    val label: String,
    val clickedCallbacks: List[() => Unit]) extends Widget {

  require(clickedCallbacks != null, "Callback list can't be null!")

  def this(label: String, clickedCallback: () => Unit) =
    this(label, List(clickedCallback))

  def this(label: String) = {
    this(label, Nil)
    println("Warning: button has no click callbacks!")
  }

  def click() = {
    // ... logic to give the appearance of clicking a physical button ...
    clickedCallbacks.foreach(f => f())
  }
}

La classe ButtonWithCallbacks gestisce sia le animazioni del bottone al momento del click che i callback. Questo viola il principio di Single responsibility. Vogliamo separare la logica del bottone (le animazioni) con la logica dei callback, quest’ultima è quella che chiamiamo mixin.
